# 0001-i18n-架构

- **状态**：已采纳
- **日期**：2026-08-17
- **决策者**：architect

## 背景

项目开源在即，`UserTexts.cs` 39 条中文文案全部硬编码为 `const string`，另有散落硬编码中文（MessageRouter/CommandHandler/DownloadCoordinator/CaptionBuilder/ConfigParser）。需求：中英双语、可扩展（其他开发者可自行添加语言，不允许硬编码 switch）、per-user 语言存储与切换、ConfigParser 错误双语化。

## 方案对比

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |
| A：.resx + ResourceManager | .NET 标准；VS 工具支持 | 自包含单文件发布下 satellite assembly 处理复杂（需 IncludeAllContentForSelfExtract）；`InvariantGlobalization=true` 下文化行为需额外验证；加语言需重新编译并依赖资源管线；不支持运行时注册 |
| B：自定义字典 + 嵌入式 JSON + `LanguageCatalog.Register` | 单文件发布零障碍；注册式 API 满足"可扩展、无硬编码 switch"；JSON diff 友好；测试简单 | 无 VS 工具支持（本项目无 UI，无影响） |
| C：外部 JSON 文件目录（热加载） | 加语言不重新编译 | 需新增语言目录配置键 + 文件系统安全面；启动期 IO 依赖；无插件体系收益低 |

语言上下文传播亦对比：A 显式传参（`InboundMessage.Language` + 方法参数）vs B AsyncLocal 隐式上下文。B 不可测试、易泄漏、难追溯。

## 决策

- **资源组织选 B**：内置 `en`/`zh` 嵌入式 JSON；`UserTexts` 转为键常量容器；`II18n.Get(lang, key, args)` 缺键回退 `en` → 键名。语言注册：`LanguageCatalog.Register(lang, dict)`。若未来需要热加载，可在 B 之上加目录加载器，接口不变。
- **语言解析链（高→低）**：per-user 显式选择 → `user.language_code`（`NormalizeLanguageCode` 前缀映射，`zh*→zh`、`en*→en`）→ 全局 `TgdlLanguage`（新配置键，默认 `auto`）→ 内建 fallback `en`。auto 的解析结果不落盘。
- **per-user 存储**：`StateDir/languages.json`（userId → lang，仅显式选择落盘），内存 `ConcurrentDictionary` + 原子写（临时文件 + rename）。首次私聊弹语言选择键盘（`lang:` 回调，仅点击者本人生效，2 分钟超时）。
- **上下文传播选显式**：`InboundMessage` 新增 `Language` 字段，消息入口解析一次；后台通知沿用触发消息语言。新增 `/language [en|zh]` 命令。
- **ConfigParser 错误双语化**：启动期无用户上下文（配置加载失败时用户也无法自救），采用**中文+英文双行并列**消息，不依赖语言探测（避免启动期鸡生蛋）；测试断言策略：只断言键名不断言全文本（现有 ConfigParserTests 仅断言异常类型，不受影响）。

## 后果

- 正面：文案单一来源（资源文件）、键集合可测试（en/zh 键一致）；加语言 = 一个 JSON + 一行注册；单文件发布无资源管线包袱；现有测试无需改断言文本。
- 负面：调用点迁移面大（约 10 个文件）；显式传参使部分方法签名增加语言参数；`CaptionBuilder` 等静态工具需改为实例/注入或增加参数。
- 实现注意：`LanguageCatalog` 与 `II18n` 必须在 AppHost 装配早期初始化；`UserLanguageStore` 目录依赖 `StateDir`（见 `0002-bot-配置管理.md`）；首次弹窗需内存去重防并发竞态。
