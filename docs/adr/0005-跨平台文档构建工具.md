# 0005-跨平台文档构建工具

- **状态**：已采纳
- **日期**：2026-08-17
- **决策者**：architect / 用户

## 背景

文档构建目前依赖 `build-docs.sh`（bash），存在三重问题：

1. **平台受限**：bash 脚本在 Windows 不可用，macOS 可用但依赖 bash 环境，无法做到三平台一致的一条命令。
2. **已知坑未根治**：
   - docfx metadata 会 restore 项目并覆盖 `project.assets.json`（不含 linux-x64 RID），导致脚本内 `dotnet publish --no-restore` 报 NETSDK1047；
   - docfx 增量缓存（`src/TGBot/obj/docfx`）导致 yml 旧时间戳不更新；
   - docfx 未安装时仅靠 bash 的 `command -v` 检测，无跨平台等价物。
3. **不可测试、不可维护**：bash 编排逻辑无法单测，行为随平台漂移。

用户诉求：文档构建脚本改用 C# 编写、跨平台（Windows/macOS/Linux 同一条命令），并已选定**方案 B：独立 C# 工具项目**（`tools/` 目录，`dotnet run --project tools/TgdlDocBuilder`）。部署脚本 `scripts/install.sh` 与 `/update` 资产平台化明确不在本次范围。

详见设计文档 `docs/design-doc-builder.md`。

## 方案对比

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |
| A：MSBuild target（.targets + dotnet msbuild 调用） | 无新目录，随 slnx 一起 | docfx 是全局工具而非 NuGet 包，无法 PackageReference 引入；进程编排/缓存清理/错误提示在 MSBuild 里表达别扭；调试与测试困难；入 slnx 会牵连主构建 |
| B：独立 C# 工具项目（`tools/TgdlDocBuilder`） | 单一命令三平台一致；纯 BCL 零依赖；编排顺序明确可维护；可系统性解决 NETSDK1047 与缓存坑；后续可扩展 | 新目录维护成本；不入主 slnx 需单独构建验证；docfx 全局工具仍需用户安装 |
| C：保留 bash + 新增 ps1 双脚本 | 改动最小 | 双脚本行为漂移、双倍维护；Windows ps1 需完整重写等价逻辑；坑 1/2 仍存在 |

## 决策

选 **B：独立 C# 工具项目 `tools/TgdlDocBuilder`**（net10.0、零第三方依赖、不入 TGBot.slnx）。

关键子决策：

- **执行顺序**：docfx 检测 → 清理 `src/TGBot/obj/docfx` 缓存 → `dotnet publish`（不带 `--no-restore`，输出临时目录）→ `docfx build docfx/docfx.json --warningsAsErrors`。先 publish 后 docfx 从根上消除 NETSDK1047（publish 之后不再有依赖 assets.json 的 MSBuild 操作）。
- **docfx 发现回退链**：`docfx` → `dotnet docfx`（覆盖 `~/.dotnet/tools` 未入 PATH 的 macOS/Linux 场景，不修改 PATH）；仍失败输出安装指引并返回非零。
- **tools 不入 slnx**：隔离主构建/测试/CI；工具零依赖无需 slnx 管理；编译验证靠 `dotnet run`（含 build）与 dev 合流时的 `dotnet build tools/TgdlDocBuilder`。
- **工具项目不加 GenerateDocumentationFile**：0 警告硬门槛的动机是 docfx 生成 TGBot API 文档的质量；工具自身不产文档不进镜像，XML 注释收益为零（编译警告仍须 0）。界定写入 AGENTS.md。
- **DOTNET_ROOT 不自动设置**：属本机运行时布局问题，文档说明即可（`export DOTNET_ROOT=$HOME/dotnet`）。
- **不建工具单测**：薄编排 + 进程调用 mock 成本高，三平台人工验收覆盖核心风险。

## 后果

- 正面：
  - 单一命令 `dotnet run --project tools/TgdlDocBuilder` 三平台一致，行为确定；
  - NETSDK1047 与增量缓存坑在工具内系统性解决，不再依赖运维人员记忆；
  - 编排逻辑为普通 C# 代码，可读、可维护、可演进（参数、错误提示）；
  - `build-docs.sh` 删除后单一入口，无脚本漂移。
- 负面：
  - 新增 `tools/` 目录维护面（但零依赖、单文件，成本低）；
  - 工具不入主 slnx，编译错误不被主 CI 捕获（缓解：`dotnet run` 即编译 + dev 合流验证时顺手构建）；
  - docfx 仍为外部全局工具依赖，需用户自行安装（与现状一致）。
- 迁移/实现注意：
  - 删除 `build-docs.sh` 后须同步 README / README.en / CONTRIBUTING / AGENTS.md / `.opencode/agent/docs.md` / `.opencode/command/doc.md` / `docfx/index.md` 中的命令引用（清单见设计文档 §7）；
  - Windows 下删除缓存目录前须递归清只读属性（`Directory.Delete(recursive:true)` 对只读文件抛 IOException）；
  - 子进程输出不重定向（继承控制台）以实时透传并避免管道死锁。
