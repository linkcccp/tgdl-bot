# 0004-多架构镜像发布与架构感知更新

- **状态**：已采纳
- **日期**：2026-08-17
- **决策者**：architect / 用户

## 背景

用户确认需要支持 **arm64**（不做 armv7/32 位）：CI 发版产出 x64 + arm64 的 multi-arch manifest 镜像（platform 为 `linux/amd64`（标准平台串，amd64 即 x64）与 `linux/arm64`；`docker pull` 自动按宿主架构拉取，`install.sh` 无需改动），且**代码层面保证 `/update` 在 arm 上可用**。

现状约束与事实：

- 所有第三方依赖的 arm64 资产均已确认存在：tba fork `linkcccp/telegram-bot-api` latest Release 已发布 `telegram-bot-api-linux-arm64`；johnvansickle 提供 `ffmpeg-release-arm64-static.tar.xz`；yt-dlp 官方有 `yt-dlp_linux_aarch64`（与 x64 的 `yt-dlp` 官方 x86_64 命名资产分列）；deno 有 `deno-aarch64-unknown-linux-gnu.zip` 且 Dockerfile 已有 `TARGETARCH` 分支。
- `release.yml` 现状：publish 仅 linux-x64、tba/ffmpeg/yt-dlp 下载全部硬编码 x64 资产、buildx 单平台 `linux/amd64`（标准平台串）。
- `src/TGBot/Update/ToolSource.cs`：`FfmpegToolSource.ReleaseUrl` 与 `YtDlpToolSource.LatestUrl` 硬编码 x64 资产（官方 x86_64 命名）URL——arm64 容器内 `/update` 会下载无法执行的 x64 二进制。
- 本机为 x64（x86_64）：arm 镜像只能验证构建成功，真实运行由用户日后在 ARM 设备实测。

## 方案对比

### 决策点 1：CI 多架构构建方式

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |
| A：matrix 双 job（x64 `ubuntu-latest` + arm64 原生 runner `ubuntu-24.04-arm`），各构建各镜像推 per-arch tag，`buildx imagetools create` 合并 multi-arch tag | 原生构建快（无 QEMU 3-5 倍损耗）；下载的 arm64 二进制可在 runner 上原生执行校验（`yt-dlp --version` / `ffmpeg -version`）；arm runner 对 public 仓库免费，成本为零；per-arch tag 隔离两 job 互不阻塞 | 需两条 runner；多一个 manifest 合并 job；arm64 镜像无法在 x64 runner 上运行时冒烟（接受，交用户实测） |
| B：单 x64 job + `docker/setup-qemu-action`，buildx 一次 `--platform linux/amd64,linux/arm64` | 无需新 runner；流程与现状最接近 | QEMU 模拟慢 3-5 倍且偶发兼容性问题；下载的 arm64 二进制无法原生执行校验；可靠性低 |

### 决策点 2：/update 运行期架构检测与异常架构回退

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |
| A：`RuntimeInformation.ProcessArchitecture` 选择对应架构 URL；非 x64/arm64 **快速失败**（抛 `InvalidOperationException`） | 进程架构即宿主架构，无环境变量/探测误差；错误立即暴露；下载前拦截，不浪费流量；纯函数可单测 | 新增一个静态工具类与构造参数（成本极低） |
| B：未知架构静默回退下载 x64 | 实现最简单 | 错误架构二进制必然在 `VerifyBinaryAsync`（下载后执行 `--version`）失败——错误被推迟到下载完成之后，报错绕且浪费流量；掩盖部署错误 |

## 决策

- **命名约定（防混淆，追加于评审后）**：所有人为可读**自命名统一 `x64` / `arm64`**（dist 目录 `docker/dist/{x64,arm64}/`、镜像 per-arch tag `{ver}-x64` / `{ver}-arm64`、CI matrix 变量 `distarch`、步骤名/注释/echo 文本、文档与 ADR 正文），`amd64` 不出现在任何自命名位置；**Docker 标准平台串**（`linux/amd64` / `linux/arm64`、`TARGETARCH` 注入值 amd64/arm64）与**第三方官方资产命名/URL**（ffmpeg 的 `amd64` 后缀、yt-dlp 的 `x86_64`/`aarch64` 命名、deno 的 `x86_64`/`aarch64` 命名）保留原样，提及处加注「amd64 即 x64」/「标准平台串」。Dockerfile 新增 `ARG DISTARCH=x64`（CI 显式传）驱动 COPY 路径，`TARGETARCH`（buildx 自动注入）仅保留给 deno 分支判断。
- **CI 选 A（matrix 双 job + 原生 arm runner + imagetools 合并）**：`build` job matrix 含 x64（`ubuntu-latest`）/ arm64（`ubuntu-24.04-arm`），各下载对应架构资产、publish 对应 RID、构建并推 per-arch tag（`{ver}-x64` / `{ver}-arm64`）；`manifest` job（`needs: build`）用 `docker buildx imagetools create` 合并出 `{ver}` 与 `latest` 双平台 tag，并断言 manifest 含两个 platform，随后只在该 job 建一次 GitHub Release。`latest` 不按架构推。
- **tba 资产缺失即 CI 硬失败**：matrix 各 job 沿用现有"资产不存在 → `exit 1`"模式（含 ELF 魔数校验 + 重试），**不静默降级到 x64**——若 fork 某版本缺 arm64 资产，发版流程显式失败，由维护者跟进 fork 发布而非产出坏镜像。
- **/update 选 A（运行时架构感知 + 快速失败）**：新建 `TGBot.Update.ToolArch` 静态类，`FfmpegReleaseUrl(arch)` / `YtDlpReleaseUrl(arch)` 按 `RuntimeInformation.ProcessArchitecture` 映射 URL（`X64` → x64 资产（官方 amd64 命名），`Arm64` → arm64 资产，其余 → 抛异常）；`YtDlpToolSource` / `FfmpegToolSource` 构造函数增加可选 `Func<Architecture>? archProvider = null`（默认取真实进程架构，AppHost 调用点零改动），URL 常量改为实例字段。yt-dlp 的 HEAD 重定向版本探测与 ffmpeg 版本页解析逻辑不变。镜像构建期 seed-bin 与镜像同架构，entrypoint 无需感知架构。

## 后果

- 正面：
  - 双架构原生构建，速度与可靠性优于 QEMU；arm runner 对 public 仓库免费，无新增成本。
  - `install.sh` 与 entrypoint 零改动，既有部署链路完全兼容。
  - arm64 资产在 CI 内被原生执行校验（yt-dlp/ffmpeg 在 arm64 runner 上跑版本命令），坏资产在发版前暴露。
  - `/update` 在 arm64 容器内下载 arm64 二进制，错误架构（误部署/未来新增架构）快速失败且报错清晰。
  - 自命名统一 x64/arm64 后，dist 目录、per-arch tag、matrix 变量与文档表述一致，消除 `amd64`/`arm64` 视觉混淆导致的人为失误。
- 负面：
  - 每次发版在 GHCR 遗留 2 个 per-arch tag（`{ver}-x64` / `{ver}-arm64`），作为 manifest 组成来源保留（不可变资产，可接受）。
  - arm64 镜像的运行时行为（bot 本体、tba、下载流程）无法在 CI 验证，真实运行依赖用户 ARM 设备实测，期间 arm64 支持标记为"待实测"。
  - 依赖 tba fork 持续发布 arm64 资产；缺失时发版失败（已通过硬失败策略显式化，但需要维护者及时跟进 fork 发布）。
  - Dockerfile 需新增 `ARG DISTARCH=x64` 并把第 42-45 行四条 COPY 改为 `dist/${DISTARCH}/`（含 yt-dlp），否则 arm64 镜像内 seed-bin 会是 x64 二进制；**COPY 指令不能用 shell 替换，必须显式 ARG**。
- 迁移/实现注意：
  - dist 布局改为 `docker/dist/{x64,arm64}/`，四个二进制全部 per-arch 存放（含 yt-dlp）。
  - `ToolArchTests` 必须参数化注入架构（本机 x64 跑不到 arm64 分支，是唯一覆盖途径）。
  - release.yml 的 Release 创建与 manifest 合并只在 `manifest` job 执行一次，避免重复建 Release。
  - 详细设计见 `docs/design-arm64-support.md`。

## 勘误（2026-08-17，不改变已采纳决策）

- 正文"URL 常量改为实例字段"与实际实现不符：实现为**删除 URL 常量**，`YtDlpToolSource`/`FfmpegToolSource` 改为持有 `Func<Architecture> _archProvider`，URL 在**调用点动态解析**（`ToolArch.XXXReleaseUrl(_archProvider())`）。URL 单一数据源集中在 `ToolArch`，注入更灵活（测试注入的架构每次调用时生效）。决策本身（`ToolArch` 静态类 + 可选 `archProvider` 构造参数 + 快速失败）不变。
