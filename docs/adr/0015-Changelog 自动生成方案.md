# ADR 0015: Changelog 自动生成方案

## 状态
已采纳

## 日期
2026-09-03

## 背景

当前 CHANGELOG.md 由维护者手动维护，存在以下问题：
1. 容易遗漏 commit
2. PR 和 Issue 编号需要手动关联
3. 格式不一致
4. 消耗维护者时间

需要在 release 构建时自动生成 changelog，包含：
- 两个版本之间的所有 commit（按类型分组）
- PR 编号（如果 commit 对应 PR）
- Issue 编号（如果 commit 或 PR 引用了 issue）
- 避免重复列举

## 决策驱动因素

1. **自动化**：减少维护者手动工作
2. **准确性**：自动关联 PR 和 Issue
3. **一致性**：统一的格式和分组
4. **可追溯性**：每个改动都能追溯到 PR 和 Issue

## 方案对比

### 方案 A：手动维护（现状）

**优点**：
- 完全控制内容
- 无需引入新工具

**缺点**：
- 消耗维护者时间
- 容易遗漏
- 格式不一致
- PR/Issue 关联困难

### 方案 B：git-cliff（采用）

**优点**：
- 专业的 changelog 生成工具
- 支持 conventional commits
- 支持 PR 和 Issue 关联
- 配置灵活
- CI 中安装简单（npm）

**缺点**：
- 需要配置 cliff.toml
- 需要 CI 中安装

### 方案 C：github-changelog-generator

**优点**：
- GitHub 原生集成
- 自动获取 PR 和 Issue

**缺点**：
- 需要 Ruby 环境
- 配置复杂
- CI 安装较慢

### 方案 D：自定义脚本

**优点**：
- 完全定制
- 无外部依赖

**缺点**：
- 维护成本高
- 需要处理各种 edge case
- 无法复用社区经验

## 决策

采用**方案 B：git-cliff**。

理由：
1. git-cliff 是专业的 changelog 生成工具，社区活跃
2. 支持 conventional commits 和 PR/Issue 关联
3. 通过 npm 安装，CI 环境友好
4. 配置灵活，可满足项目需求

## 详细设计

### 1. cliff.toml 配置

```toml
[changelog]
# changelog header
header = """
# 更新日志 / Changelog\n
本项目遵循 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 格式
（中文为主、英文并存，与 README 策略一致）。\n
"""
# template for the changelog body
# https://docs.git-cliff.org/templates/body/
body = """
{%- macro remote_url() -%}
  https://github.com/linkcccp/tgdl-bot
{%- endmacro -%}
{% for commit in commits %}
  {% if commit.version %}
    ## [{{ commit.version }}] - {{ commit.timestamp | date(format="%Y-%m-%d") }}
  {% else %}
    ## [Unreleased]
  {% endif %}

  {% if commit.github %}
  > 由 [{{ commit.github.pr }}]({{ self::remote_url() }}/pull/{{ commit.github.pr }}) 合并
  {% endif %}

  {% for group, commits in commits | group_by(attribute="group") %}
  ### {{ group | striptags | trim | upper_first }}
  {% for commit in commits %}
    - {% if commit.scope %}**{{ commit.scope }}**: {% endif %}\
      {{ commit.message | upper_first }}\
      {% if commit.github.pr %} ([#{{ commit.github.pr }}]({{ self::remote_url() }}/pull/{{ commit.github.pr }})){% endif %}\
      {% if commit.github.contributors is not empty %}
      \n
      {% for contributor in commit.github.contributors %}
        &nbsp;&nbsp;- @{{ contributor }}
      {% endfor %}
      {% endif %}\
      {% if commit.footers is not empty %}
      {% for footer in commit.footers %}
        \n  > {{ footer }}

      {% endif %}

  {% endfor %}

**Full Changelog**: https://github.com/linkcccp/tgdl-bot/compare/{{ previous.tag }}...{{ version }}

### 2. release.yml 修改

在 manifest job 中添加 changelog 生成步骤：

```yaml
  manifest:
    name: Merge manifest & create Release
    needs: [check, build]
    if: needs.check.outputs.should_release == 'true'
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v7
        with:
          fetch-depth: 0  # 需要完整历史来生成 changelog

      - name: Resolve version
        shell: bash
        run: |
          echo "VERSION=${{ needs.check.outputs.version }}" >> "$GITHUB_ENV"
          echo "TAG=${{ needs.check.outputs.tag }}" >> "$GITHUB_ENV"

      # 获取上一个 tag
      - name: Get previous tag
        id: prev_tag
        shell: bash
        run: |
          # 获取当前 tag 之前的上一个 tag
          PREV_TAG=$(git tag --sort=-v:refname | grep -E '^v[0-9]+\.[0-9]+\.[0-9]+$' | sed -n '2p')
          if [ -z "$PREV_TAG" ]; then
            # 如果没有上一个 tag，使用第一个 commit
            PREV_TAG=$(git rev-list --max-parents=0 HEAD | head -1)
          fi
          echo "prev_tag=$PREV_TAG" >> "$GITHUB_OUTPUT"

      # 安装 git-cliff
      - name: Install git-cliff
        shell: bash
        run: |
          npm install -g git-cliff

      # 生成 changelog
      - name: Generate changelog
        id: changelog
        shell: bash
        run: |
          # 生成从上一个 tag 到当前 tag 的 changelog
          git cliff --tag "${{ env.TAG }}" \
            --from "${{ steps.prev_tag.outputs.prev_tag }}" \
            --to "${{ env.TAG }}" \
            -o CHANGELOG_RELEASE.md
          
          # 读取生成的 changelog
          CHANGELOG=$(cat CHANGELOG_RELEASE.md)
          echo "changelog<<EOF" >> "$GITHUB_OUTPUT"
          echo "$CHANGELOG" >> "$GITHUB_OUTPUT"
          echo "EOF" >> "$GITHUB_OUTPUT"

      # 更新 CHANGELOG.md
      - name: Update CHANGELOG.md
        shell: bash
        run: |
          # 读取现有的 CHANGELOG.md
          EXISTING_CHANGELOG=$(cat CHANGELOG.md)
          
          # 生成新的 changelog 内容
          NEW_CHANGELOG=$(cat <<EOF
          # 更新日志 / Changelog

          本项目遵循 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 格式
          （中文为主、英文并存，与 README 策略一致）。
          **版本号与 git tag 一一对应**：每个发布版本对应一个 \`v*\` tag
          （如 \`v2.4.0\`），tag 触发 CI 构建镜像并创建 GitHub Release。

          This project follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
          format (Chinese-primary with English, same policy as the README).
          **Every version maps to a git tag** (e.g. \`v2.4.0\`); pushing the tag triggers CI
          to build the Docker image and create a GitHub Release.

          ${{ steps.changelog.outputs.changelog }}

          ## 历史版本 / Previous Releases

          较早版本（v2.3.1 及更早）无独立更新日志，变更内容见对应 git tag 与
          [GitHub Releases](https://github.com/linkcccp/tgdl-bot/releases)。

          Earlier releases (v2.3.1 and before) do not have a dedicated changelog; see the
          corresponding git tags and [GitHub Releases](https://github.com/linkcccp/tgdl-bot/releases)。
          EOF
          )
          
          # 写入新的 CHANGELOG.md
          echo "$NEW_CHANGELOG" > CHANGELOG.md

      # imagetools 需要 buildx；GHCR 登录凭据 job 间不共享，manifest job 内需重新登录
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v4

      - name: Login to GHCR
        uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # 合并 per-arch tag -> multi-arch manifest（{ver} 与 latest 一次建两个）
      - name: Merge multi-arch manifest (${{ env.VERSION }} + latest)
        shell: bash
        run: |
          set -euo pipefail
          docker buildx imagetools create \
            -t "ghcr.io/linkcccp/tgdl-bot:${VERSION}" \
            -t "ghcr.io/linkcccp/tgdl-bot:latest" \
            "ghcr.io/linkcccp/tgdl-bot:${VERSION}-x64" \
            "ghcr.io/linkcccp/tgdl-bot:${VERSION}-arm64"

      # 断言 manifest 同时包含两个标准平台串（amd64 即 x64），防合并遗漏；失败即 job 失败
      - name: Assert manifest contains linux/amd64 + linux/arm64
        shell: bash
        run: |
          set -euo pipefail
          out="$(docker buildx imagetools inspect "ghcr.io/linkcccp/tgdl-bot:${VERSION}")"
          printf '%s\n' "$out"
          grep -q "linux/amd64" <<<"$out" || { echo "错误：manifest 缺少 linux/amd64（即 x64）"; exit 1; }
          grep -q "linux/arm64" <<<"$out" || { echo "错误：manifest 缺少 linux/arm64"; exit 1; }

      # 更新 CHANGELOG.md 到仓库
      - name: Commit CHANGELOG.md
        shell: bash
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          git add CHANGELOG.md
          git commit -m "docs: update CHANGELOG.md for ${VERSION}"
          git push origin HEAD:main

      # 使用生成的 changelog 创建 GitHub Release
      - name: Create GitHub Release
        uses: softprops/action-gh-release@v3
        with:
          tag_name: ${{ needs.check.outputs.tag }}
          name: Release ${{ needs.check.outputs.tag }}
          body: |
            ${{ steps.changelog.outputs.changelog }}
            
            ---

            已发布 Docker 镜像：`ghcr.io/linkcccp/tgdl-bot:${{ env.VERSION }}`（及 `:latest`）
            平台：linux/amd64（即 x64）+ linux/arm64（multi-arch manifest，`docker pull` 自动按宿主架构拉取）

            一键部署：
            ```bash
            curl -fsSL https://raw.githubusercontent.com/linkcccp/tgdl-bot/main/scripts/install.sh | sudo bash
            ```

            说明：arm64 镜像经原生 arm64 runner 构建并完成资产原生执行校验，构建侧已验证；
            真实运行待 ARM 设备实测。armv7/32 位不支持。
```

### 3. 安装脚本（可选）

为了简化安装，可以创建一个安装脚本 `scripts/install-git-cliff.sh`：

```bash
#!/bin/bash
set -euo pipefail

# 检查是否已安装 git-cliff
if command -v git-cliff &> /dev/null; then
    echo "git-cliff 已安装"
    git-cliff --version
    exit 0
fi

# 安装 git-cliff
echo "安装 git-cliff..."
npm install -g git-cliff

# 验证安装
if command -v git-cliff &> /dev/null; then
    echo "git-cliff 安装成功"
    git-cliff --version
else
    echo "git-cliff 安装失败"
    exit 1
fi
```

## 后果

### 正面

1. **自动化**：减少维护者手动工作
2. **准确性**：自动关联 PR 和 Issue
3. **一致性**：统一的格式和分组
4. **可追溯性**：每个改动都能追溯到 PR 和 Issue
5. **可维护性**：配置集中，易于调整

### 负面

1. **CI 依赖**：需要在 CI 中安装 git-cliff
2. **配置维护**：需要维护 cliff.toml 配置
3. **学习成本**：团队需要了解 git-cliff 配置

### 风险缓解

1. **CI 安装失败**：使用 npm 安装，GitHub Actions 的 Node.js 环境成熟
2. **配置错误**：提供完整的配置示例和测试步骤
3. **性能影响**：git-cliff 执行很快，对 CI 时间影响很小

## 验证方式

### 1. 本地测试

```bash
# 安装 git-cliff
npm install -g git-cliff

# 测试生成 changelog
git cliff --tag "test-release" -o CHANGELOG_TEST.md

# 检查生成的文件
cat CHANGELOG_TEST.md
```

### 2. CI 测试

1. 推送到测试分支
2. 创建测试 tag（如 `v0.0.1-test`）
3. 检查 CI 是否成功生成 changelog
4. 检查 GitHub Release 是否包含 changelog

### 3. 验证清单

- [ ] cliff.toml 配置正确
- [ ] CI 能成功安装 git-cliff
- [ ] 生成的 changelog 包含 PR 编号
- [ ] 生成的 changelog 包含 Issue 编号
- [ ] 生成的 changelog 格式正确
- [ ] CHANGELOG.md 能正确更新
- [ ] GitHub Release 包含完整的 changelog

## 迁移步骤

1. **准备阶段**：创建特性分支，添加 cliff.toml
2. **测试阶段**：在测试分支验证 CI 流程
3. **发布阶段**：合并到 main，打 tag 验证完整流程

## 回滚方案

如果新流程有问题，可以：
1. 删除 cliff.toml
2. 恢复 release.yml 原有配置
3. 手动维护 CHANGELOG.md

所有改动都在 Git 中，可以快速回滚。
